# HiCodeer 防侵权修改记录

> 归档：2026-10-04。代码改动见 commit `68e657a`（25 个文件）；此后追加的
> 语言裁剪见第 3.5 节。
> 本文记录 HiCodeer 为规避对 Zed 及其运营服务的依赖所做的全部代码改动。
> 全文分两部分：**网络出口**（发不出去）与**用户可见面**（不露出），外加
> 配套改动与门控纪律。

## 0. 方案总览

HiCodeer 不使用 Zed 的代码、资产、编译产物与网络服务。改动落在两处收口：

**网络出口** — DNS 解析层与 `open_url` 层各拦一次，保证任何指向 Zed 域名的
报文都发不出去。

**用户可见面** — 界面不显示依赖 Zed 的功能入口、配置项与文案。

配套改动处理落盘字符串、默认配置、译文、git 身份等。

所有对上游共享代码的改动都用 `#[cfg(target_env = "ohos")]` 门控隔离，非
OHOS 平台编译与行为不变（核查结论见第 5 节）。

## 1. 网络出口拦截

### 1.1 判定规则（唯一来源）

新增 `crates/gpui_ohos/depend/ohos-libc-shim/src/blocked_host.rs`，113 行，
是整个拦截的唯一规则来源。两个入口：

- `host_is_blocked(host: &str) -> bool`（:34）—— 判主机名
- `url_host_is_blocked(url: &str) -> bool`（:42）—— 从 URL 里取出 host 再判

匹配规则（:25-29 的三个常量）：

- 先按点分段，只看 host，不看路径与查询串
- 某标签**等于** `zed` ⇒ 命中
- 某标签**以 `zed-` 开头** ⇒ 命中（这一条覆盖 `zed-industries` 这类形式）

判定结果：

- `zed.dev` / `api.zed.dev` / `status.zed.dev` ⇒ 命中
- `zed-industries.com` / `mail.zed-industries.com` ⇒ 命中
- `maxtrauthzed.com` / `zedsite.com` / `notzed.dev` ⇒ **不**命中（只是碰巧
  含同样字母）

`url_host_is_blocked` 对没有 `://` 的字符串（如 `mailto:hi@zed.dev`）与
`zed://` 这类自定义 scheme 一律判为不命中，只处理真正的层级 URL。

文件内附 5 个单元测试（:67-113），覆盖上面每一条，含三条明确不拦的对照
（`github.com/zed-industries/zed`、`mailto:hi@zed.dev`、
`zed://git/clone?repo=...github.com/zed-industries/zed`）。

### 1.2 DNS 层

`getaddrinfo` 是所有主机名解析的唯一入口，拦它就同时覆盖 HTTP、WebSocket、
gRPC 等所有走 `TcpStream::connect` 的路径。

- `crates/gpui_ohos/depend/launch-zed/build.rs:26` —— 在既有 9 个路径相关
  符号之后，把 `"getaddrinfo"` 加进 `--wrap` 列表
- `crates/gpui_ohos/depend/ohos-libc-shim/src/ohos_libc_shim.rs:448` ——
  `__wrap_getaddrinfo` 实现
- 同文件 :441 —— `const EAI_NONAME: c_int = -2`（libc crate 不导出 `EAI_*`
  家族，字面写出）
- 同文件 :461 —— 未命中时转发给 `__real_getaddrinfo`（:265 声明）
- 同文件 :467 —— `node_is_blocked()`，处理 `node` 为 null（调用方只问端口号）
  与非 UTF-8 两种情况

两个设计要点：

1. **返回 `EAI_NONAME` 而不是自造错误码**。这个码的含义是"域名解析不出来"，
   调用方对它已有处理路径，于是被拒的域名与拼错的域名**不可区分**，上层不会
   冒出未预期的错误分支。
2. **必须转发给 `__real_getaddrinfo`，不能用 `libc::getaddrinfo`**。后者走
   `#[link_name]` 符号调用，会被自己的 wrapper 再捕获一次，直接无限递归。

拦截时打一条 `warn!`（:479）记录被拒的域名。这是判断拦截是否生效的唯一
可见证据。

### 1.3 `open_url` 层

`cx.open_url()` 最终落到 `crates/gpui_ohos/src/ohos/platform.rs:591` 的
`OhosPlatform::open_url`，它把 URL 交给系统浏览器。**浏览器在 Rust 进程
外解析域名，DNS 拦截看不到它** —— 这是必须单独拦的原因。

`platform.rs:595` 调 `blocked_host::url_host_is_blocked(url)`，命中则打
`warn!`（:596）并直接 `return`，不交给系统。

### 1.4 与既有 `--wrap` 的关系

`build.rs` 原本的 9 个符号（`open` / `openat` / `access` / `stat` / `lstat`
/ `fstatat` / `opendir` / `realpath` / `syscall`）是给 OHOS picker grant
重新激活用的，与拦截无关。`getaddrinfo` 是第 10 个，用途不同，但复用同一
套 `--wrap` 机制。文件头注释已说明这个区别。

### 1.5 验证

- `nm` 读产物：`T __wrap_getaddrinfo` 已导出；`U getaddrinfo` 只剩一处
  未定义引用（即 wrapper 内部转发给 `__real_` 的那次），没有符号能绕过
- 两处 `refused blocked host` 文案都在 `libhicodeer.so` 里，确认代码编进去了
- 5 个单元测试通过
- 设备实测：DNS 拦截生效

### 3.5 语言：只留中文，其余回退英文

界面语言只保留**简体中文**与**英文**两种。英文是源语言（`index.json` 里
`en-US` 的 `bundle` 为 `null`），词典的 key 本身就是英文原文，查不到译文时
回退到 key，所以英文不需要任何文件。

具体做法是删掉 `assets/locales/` 下 12 个多余词典
（`cs-CZ` / `de-DE` / `es-ES` / `fr-FR` / `it-IT` / `ja-JP` / `ko-KR` /
`pl-PL` / `pt-BR` / `ru-RU` / `tr-TR` / `zh-TW`），并把
`assets/locales/index.json` 的 `locales` 列表从 14 条减到 2 条
（`en-US` + `zh-CN`）。

**回退链是现成的，不需要额外代码**（`crates/localization/src/localization.rs:375`
的 `resolve_locale`）：用户偏好、legacy 标记、系统语种三条入口，任何一条
匹配不上都归到 `EnglishFallback` → `resolved_locale = "en-US"` →
`bundle: null` → `Self::english(...)`。系统语言是日/韩/俄/繁体时界面显示
英文，不崩、不 fallback 到别的语言。

**语言选择器会自动跟着变**：`localization.rs:344` 的 `available_locales()`
直接透传 `index.locales`，所以设置界面的语言列表只剩两项，无需另改。

词典由 `rust_embed` 按 `#[include = "*.json"]` glob 收集
（`localization.rs:13-14`），文件删了就自动少嵌一份，**不需要改任何构建
配置**。这一步也让 HAP 少了约 8.6 MB 的死资源。

`index.json` 的 `catalog_sha256` / `source_formats`（485 条）/
`source_locale` / `zed_commit` / `zed_version` 全部未动 —— `catalog_sha256`
是 `zh-CN.json` 的校验字段，改 `locales` 列表不影响它。

**简体与繁体**：繁体（`zh-TW`）已按决定删除，繁体系统语种会回退到英文。

**新增译文**：`zh-CN.json` 新增一条 `API Key for authentication` →
`API KEY用于认证`。走词典而非硬编码中文字面量，是为了不破坏 i18n（英文环境
下也会显示中文）。新增独立 key 而非改共享的 `API Key` 条目，是为了不波及
`llm_providers_page.rs` 内那两处语义不同的 API Key 标签。

**⚠ 本节只做了「裁语种」，没做「改内容」。** `zh-CN.json` 本身仍是上游原文，
翻译里还有大量 Zed 品牌、zed 域名、以及含 zed 的 key。这条列在第 6 节遗留项
第 3 条。

## 5. 门控纪律

### 5.1 硬约束

所有对上游共享代码的改动**必须**用 `#[cfg(target_env = "ohos")]` 门控。
`target_env` 下改共享代码的语义会原样改变 macOS / Linux / Windows 的行为。

不可门控的位置用 `[OHOS PORT BEGIN/END]` 注释对标注；OHOS 专属文件
（`crates/gpui_ohos/**`、`hap/**`、`patches/**`）加头注释。门控块内的注释
一律英文。

**写门控时的语法陷阱**（本项目多次踩到）：

- `#[cfg]` 不能插在方法链 `workspace.a().b()` 中间
- `let` 不能出现在结构体字面量的字段位置
- `let` 不能出现在函数调用的参数位置
- `#[cfg]` 裸属性后不能直接跟表达式
- 同一语义要分支时，用「一对互斥的局部 `let`」而不是改已有行

`cfg!` 宏**不能**用来做这类门控：它展开成运行期 `bool`，两个分支都会编译，
既消不掉代码也消不掉字符串常量。

### 5.2 交付前的门控自查

判据：**「删除了已有行，却没有 `#[cfg]`」的 hunk** —— 那才是真正会影响非
OHOS 平台的地方。纯新增行若在 `#[cfg]` 块内则安全。

本轮自查发现并修掉 1 处漏洞：`edit_prediction_button.rs` 的 `View Docs`
菜单项与 `PRIVACY_DOCS` 常量曾被无条件删除，非 OHOS 平台会少一项。已改为
`#[cfg(not(target_env = "ohos"))]` 常量 + `view_docs_item: Option<ContextMenuEntry>`
+ `.when_some(...)`。

自查为**静态核查**。本机只装了 `aarch64-unknown-linux-ohos` 一个 target，
编不了非 OHOS 版本，所以「非 OHOS 平台编译通过且功能不变」这件事尚未经过
编译验证，只经过逐 hunk 的人工比对。

### 5.3 几处看着可疑但确认无害的

静态核查里有几处 hunk 报了警，逐一确认后是误判，记在这里免得下次重查：

- `feedback.rs` 的 `cx.open_url(HICODEER_REPO_URL)` —— 看着像裸改，但该常量在
  `not(ohos)` 分支的值就是原 `ZED_REPO_URL` 的值
- `paths.rs` 三处 —— 只是把 `.zed/...` 字面量换成函数调用，函数两平台返回值
  相同
- `title_bar.rs` / `git/repository.rs` —— 变量在 `not(ohos)` 分支分别恒为
  `true` / `("Zed", "hi@zed.dev")`，与原值一致
- `page_data.rs` 的 `network_section` —— 看着像「交换了 Proxy 与 Server
  URL」，实际非 OHOS 下 `[Header, Proxy] + chain(Server URL)` 就是原来的
  `[Header, Proxy, Server URL]`，顺序未变
- `edit_prediction_provider_setup.rs` 三个 `+ "API Key"` —— 是给上游调用点补
  的新参数，值与原函数体里的 `localized_str!("API Key")` 一致

**一处确实没清干净的例外**：`crates/zed/src/main.rs` 里
`localized_str!("Zed failed to launch")` 与 `"dev.zed.Oops"` 两个既有字面量
在 OHOS 下仍会编进产物。这不是本次引入的，且那段代码在 ashpd 桌面分支内、
OHOS 走不到，也不是 URL。
