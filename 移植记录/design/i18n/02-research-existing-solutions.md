# 第 2 章 调研：外部有没有现成方案

## 2.1 结论先行

- **Zed 官方没有 i18n**。
  - `zed-industries/zed` 的 issue **#7409「Localization」/「Localization and support for different locales」**于 **2024-02 开**，至今仍 open，**无官方回应**。
  - 官方 roadmap 里**没有** i18n 条目。
  - （网络事实，本轮未联网复核，标注；来源见下方社区候选同样标注。）
- **没有任何「丢个语言包就生效」的运行时方案**——即不存在一个「装上就能让英文 Zed 显示中文、且不改源码」的机制。
  - 原因：Zed（GPUI）的界面文案是编译进二进制的 Rust 字面量，运行时没有可替换的资源层。
  - 结论：**汉化只能走「改源码重新编译」**这条路。

## 2.2 三个社区候选

以下星数 / 许可证 / 维护状态属**外部网络事实**，本轮未联网复核，标注「未核实」；方案性质（汉化方式、组织方式）来自对候选仓库的调研记录。

### 候选 A：`LI-NA/zed-i18n`（**我们选它**）

- 星数：118。
- 许可证：**内容侧 GPL-3.0 + 工具侧 MIT**（其 crate 声明 `GPL-3.0-or-later`）。
- 汉化方式：**工具链式**——提取（extract）→ 翻译 → 回注（apply）→ 编译。
- 覆盖版本：对齐上游 `v1.21.0`（实测 tag `v1.21.0-i18n.1`）。
- 维护状态：**活跃**，最后提交 `c45ba0f`，日期 2026-09-25，主题 `feat: update Zed to v1.21.0`（实测，见第 4 章）。
- 是否适合我们：**适合**。理由：工具链式且以字节偏移定位回注，能对准我们自己的源码树；许可证与 GPL-3.0-or-later 相容。

### 候选 B：`TC999/zed-loc`

- 星数：427。
- 许可证：MIT。
- 汉化方式：**每晚自动构建**。
- 覆盖版本：翻译表按**文件路径**组织（`某文件的某句 → 译文`）。
- 问题：**版本一变即失效**（上游文件路径 / 行号一动，整张表就错位）；且其**提取脚本仅 Windows 可跑**。
- 是否适合我们：**不适合**。我们是 Linux（OHOS target），且版本与上游差两档。

### 候选 C：`x6nux/zed-globalization`

- 星数：1005。
- 汉化方式：**整包分发**——直接发布预编译好的中文版 Zed。
- 问题：**夹带与汉化无关的改动**；且是整包，无法把「汉化」这件事**回注**到我们自己的源码树里。
- 是否适合我们：**不适合**。我们要的是「在我们的 1.23 树上落地多语种」，不是换成别人的整包。

## 2.3 排除项及理由

- `Nriver/zed-translation`、`xxk8/zed-cn`：**AGPL-3.0**，与 GPL-3.0-or-later 交付物冲突，且**停更**。
- `rxp200/zed-cn`：**未声明许可证**，风险不可控。

## 2.4 关键判断

- 没有任何运行时方案 → 必须走「改源码重新编译」。
- 走「改源码重新编译」就要选一个**能对准我们自己的源码树**的工具，而不是「别人的成品包」。
- 因此：**选 `LI-NA/zed-i18n`**——它提供的是「提取 + 回注」的工具链，作用对象是**我们自己的树**。
