### 1.2 两个必须先记住的前提事实

后面所有改动都由这两条推出，新版本移植时先确认它们是否仍成立：

1. **OHOS 的 `target_os` 报告为 `"linux"`**，但既没有 X11/Wayland，也没有 ALSA、XDG 桌面门户（ashpd）、`scap`/`x11` 这些 Linux 桌面栈。
   → 因此**每一处 `#[cfg(target_os = "linux")]` / `target_os = "freebsd"` 都必须复核**，通常要追加 `not(target_env = "ohos")`。
2. **OHOS 应用沙箱禁止 `exec` 任意二进制、禁止 `symlink(2)` / `hard_link(2)`、单进程只有一个 XComponent 渲染面**（单窗口）。
   → 这三点分别对应第 4 节（进程路由）、第 4.5 节（tar 链接回退）、第 7 节（设置页作为 tab）。

### 1.3 五种改动模式（升级时按模式批量处理最快）

- **模式 A：就近 cfg 分支**。在调用点用 `#[cfg(target_env = "ohos")]` / `#[cfg(not(target_env = "ohos"))]` 分叉。
  升级冲突最高，能收敛就按模式 C 收敛。
- **模式 B：排除 Linux 段**。给 `#[cfg(target_os = "linux")]`、`cfg(any(target_os="linux", target_os="freebsd"))` 追加 `not(target_env = "ohos")`。
  这类是机械改写，建议新版本一上来先全局搜索并统一加。
- **模式 C：模块替换**。保留原模块不动，另写 `*_ohos.rs` 提供同名公开面，用 `#[cfg]` 切换并 `pub use` 同一套名字。
  样板见 `crates/audio/src/audio.rs`（`audio_pipeline` ↔ `audio_pipeline_ohos`）与 `crates/crashes/src/crashes.rs`（`#[path]` 拆出 `crashes_desktop.rs`）。**这是抗升级的最佳模式**。
- **模式 D：类型替换**。把某个类型的来源从 `std`/`cpal` 换成本地同名类型（`Stdio`、`Child`、`DeviceId`），调用点拼写不变。
- **模式 E：整体新增**。`command/ohos.rs`、`zlog/ohos.rs` 这类纯新增文件，升级时基本不需要动（除非上游改了它们对接的接口）。

## 2 构建系统与工具链

### 2.1 `rust-toolchain.toml`：工具链降级

- **改法**：`channel = "1.98.1"` → `channel = "1.97.1"`。
- **原因**：OHOS 交叉工具链（rustup 侧）只提供特定版本的 `aarch64-unknown-linux-ohos` 预编译 std；1.98.1 在该工具链上装不出 std。
- **重放要点**：新版本 Zed 往往会抬高 `rust-toolchain.toml` 的 channel。**必须回退到 OHOS 工具链实际支持的版本**，否则连编译都起不来。先查工具链里 `rustup target list --installed` 与可安装的 `aarch64-unknown-linux-ohos` 版本再定。交叉目标固定为 `aarch64-unknown-linux-ohos`（见 `script/bundle-ohos` 的 `OHOS_TARGET`）。

### 2.2 根 `Cargo.toml`

四处改动：

1. **workspace members**：追加 `crates/gpui_ohos`、`crates/gpui_ohos/depend/launch-zed`、`crates/gpui_ohos/depend/ohos-libc-shim`，并用 `# ===== [OHOS PORT BEGIN/END] =====` 标记块包住。
2. **workspace dependencies**：追加 `gpui_ohos = { path = "crates/gpui_ohos" }`。
3. **版本 pin**：
   - `wgpu = "29.0.4"` → `29.0.3`（与 fork 版本一致；升这个版本必须同步升 fork）。
   - `wasmtime-wasi` 由 `{ version = "48", default-features = false, features = ["p2"] }` 改为 `"48"`（随 `patches/wasmtime` 调整，走默认特性）。
4. **`[patch.crates-io]` 段**（本段是移植的依赖基石，新版本必须原样保留并同步升级）：
   - path 补丁：`cap-primitives`、`rustix-openpty`、`which`、`wasmtime`、`virtiofsd` → `patches/<name>`。
   - fork：`wgpu` / `wgpu-core` / `wgpu-hal` / `wgpu-types` / `naga` → `jaffenqqcom/wgpu-zed`（tag `v29.0.3-zed.1`）。
   - fork：全部 `ohos-*` 绑定 crate → `jaffenqqcom/ohos-native-bindings-zed`（tag `ohos-xcomponent-binding-v0.3.2-zed.1`）。
   - 新增 `virtiofsd = { version = "1.14", default-features = false }`（仅 OHOS QEMU 管理 crate 用到）。

- **重放要点**：
  - `which` 的 patch 是"解析器钩子"，与第 4 节的远端命令解析配合（`util::command::ohos` 里的 `install_remote_which_resolver`），**不能丢**。
  - 同一 fork 树里的 crate（如 wgpu 四件套 + naga）**必须指向同一 git + 同一 tag**，否则 cargo 会解析出两份，FFI 类型不再互通。
  - 新版本若把 `wgpu` 抬到新大版本，需要先给 fork 打对应的 `v<ver>-zed.N` tag，再改这里的 pin 与 `crates/gpui_wgpu/Cargo.toml` 的 `naga`（见 2.3）。

### 2.3 crate 级 `Cargo.toml` 的两种段

统一套路：**一是给 Linux 段加 `not(target_env = "ohos")` 排除；二是加正向 `[target.'cfg(target_env = "ohos")'.dependencies]` 段。**

逐 crate：

- **`crates/gpui_platform/Cargo.toml`**：
  - Linux/FreeBSD 段追加 `not(target_env = "ohos")`（否则会拉进 `gpui_linux`）。
  - 新增 `[target.'cfg(target_env = "ohos")'.dependencies] gpui_ohos.workspace = true`。
- **`crates/gpui_wgpu/Cargo.toml`**：dev-dependency `naga` 由 `29.0.4` 改为 `29.0.3`，必须与根 pin 一致。
- **`crates/zed/Cargo.toml`**：
  - `[lib]` target 新增：`path = "src/main.rs"`、`crate-type = ["rlib"]`（供 OHOS NAPI cdylib 调 `zed::hicodeer_main()`）。`[lib]` 无法按 target gate，故所有平台都存在该 target。
  - `[dependencies]` 里 `gpui_platform` 去掉 features，改成：非 OHOS 段给 `["screen-capture","font-kit","wayland","x11"]`（`[target.'cfg(not(target_env = "ohos"))'.dependencies]`）；OHOS 保持无 feature。原因：`screen-capture` 会经 `scap` 拉进 `x11`，OHOS 编不过。
  - Linux/FreeBSD 的 `ashpd`/`image` 段、build-dependency `pkg-config` 段，全部追加 `not(target_env = "ohos")`。
- **`crates/audio/Cargo.toml`**：`cpal`/`rodio` 移入非 OHOS 段；OHOS 段用 `rodio`（`default-features = false`，去掉依赖 `cpal` 的 `playback`/`recording`）；`libwebrtc` 段追加 `not(target_env = "ohos")`。
- **`crates/call/Cargo.toml`**：`gpui` 的 `screen-capture` feature 移入非 OHOS 段。
- **`crates/title_bar/Cargo.toml`**：同上，`screen-capture` feature 移入非 OHOS 段。
- **`crates/crashes/Cargo.toml`**：`async-process` / `crash-handler` / `minidumper` / `parking_lot` / `zstd` 移入非 OHOS 段（OHOS 走存根）。
- **`crates/livekit_client/Cargo.toml`**：`libwebrtc`/`livekit`/`scap`/`webrtc-sys`/`cpal`/`rodio` 等移入非 OHOS 段；`livekit_api` 由 optional 改为非 optional（因为 OHOS 选 `mock_client` 路径统一了引用）。
- **`crates/settings_ui/Cargo.toml`**：`cpal`/`rodio` 同 `audio` 处理。
- **`crates/util/Cargo.toml`**：OHOS 段新增 `cmd-client = { path = "../gpui_ohos/depend/cmd-agent/cmd-client" }` 与 `async-tar`。

- **重放要点**：新版本上游会在这些 crate 里加入新的 Linux-only 依赖或 feature，**每次升级都要重新扫一遍**「哪些 `[target.'cfg(...linux...)']` / `screen-capture` / `cpal` / `scap` 需要排除」，而不是照抄旧结论。

### 2.4 `crates/zed` 的 lib target 与 `build.rs`

- **`Cargo.toml`**：见 2.3，新增 `[lib]`（`src/main.rs` 复用为 lib root，`rlib`）。
- **`crates/zed/build.rs`**：
  - 无条件 `println!("cargo:rustc-env=CARGO_BIN_NAME=zed");`。Cargo 只给 bin target 设 `CARGO_BIN_NAME`，但 `main.rs` 会断言它，lib 构建必须补上。
  - 所有 `#[cfg(target_os = "linux")]` / `(linux|freebsd)` 的 rpath 探测、`prepare_app_icon_x11` 相关项，追加 `not(target_env = "ohos")`（OHOS 无 pkg-config、无 libva/egl、无 X11）。
- **重放要点**：`main.rs` 顶部那个 `assert!(CARGO_BIN_NAME == "zed")` 类断言如果上游改名/去掉，`build.rs` 这行就可以重新评估；但 lib target 本身在 OHOS 上是必需的。

### 2.5 `script/clippy`

- **改法**：非 OHOS target（`CARGO_BUILD_TARGET` 不含 `ohos`）时追加
  `--exclude launch-zed --exclude gpui_ohos --exclude gpui_ohos_linker --exclude qemu-ssh-agent --exclude qemu-ssh-agent-linker`。
  另外把本地工具从 `cargo-shear` 换成 `cargo-machete`，typos 配置从 `.config/typos.toml` 换成 `typos.toml`。
- **原因**：OHOS-only crate 的非 gate 依赖（`napi-ohos`、`openharmony-ability`、本地 wgpu 树）在 macOS/Linux 编不过；`[lib]` 无法 target gate，只能靠 exclude。`qemu-ssh-agentd`、`command-executor` 故意保留（前者是 guest 侧守护进程，后者是纯 trait 定义）。
- **重放要点**：exclude 名单要与 `crates/gpui_ohos` 下的实际 crate 名对齐，新版本若增删这些 crate，此处要同步。

### 2.6 `.gitignore`

新增项：`**/build`、`*.log`、`hap/entry/libs`、`**/oh_modules`、`**/.workbuddy`、`build/`、`hap/cerfile/`、`hap/entry/hnp/arm64-v8a/hicodeerd.hnp`、`crates/gpui_ohos/depend/cmd-agent/hicodeerd/shim/musllib-shim.so`。
另有两条精细规则：`hap/entry/src/main/resources/resfile/*` 全部忽略，但 `!.../resfile/ca-bundle.crt` 例外保留（其余 resfile 是构建产物：guest 内核 Image、golden.qcow2、管理密钥等）。
- **重放要点**：CA bundle 是唯一入库的 resfile 源文件，别误删。

### 2.7 随构建流程产生的连带改动（非移植必需，但会冲突）

- `crates/gpui_macros/src/bench.rs`：bench 宏由泛型 `criterion::Criterion<gpui::BenchMeasurement>` 改为非泛型 `criterion::Criterion`，`report.print(...)` 参数改为 `Option<&str>` 形式，且把 `report` 提到循环外只打印一次。

- `tooling/xtask/src/tasks/workflows/run_tests.rs`：删除 `cargo build -p project_benchmarks --features test-support` 这一步。

## 3 平台接入

### 3.1 `crates/gpui_platform/src/gpui_platform.rs`：后端选择

- **改法**：在 `current_platform` 里新增 `#[cfg(target_env = "ohos")] { gpui_ohos::current_platform(headless) }`，并把原来的 `(linux|freebsd)` 段追加 `not(target_env = "ohos")`。
- **重放要点**：这是平台后端的总开关，必须排在所有平台相关改动之前。

### 3.2 `crates/gpui/src/app.rs`：泄漏 `Application`

- **改法**：`Application::run` 末尾新增 `#[cfg(target_env = "ohos")] { _ = Box::leak(Box::new(self)); }`。
- **原因**：OHOS 上平台运行循环由宿主 Ability 驱动，`Platform::run` 调完启动回调即返回；若正常析构，应用状态会随函数返回被释放。
- **重放要点**：与 wasm 分支（`std::mem::forget(self)`）同类。上游若重构 `Application::run` 的收尾逻辑，此分支要重新安置。

### 3.3 `crates/gpui/src/window.rs`：外部拖拽 payload 刷新

- **改法**：在 `MouseMove` 相关处理里，为"已在进行的 external drag"（`cx.active_drag` 的 value 能 downcast 成 `crate::ExternalPaths`）新增 `else` 分支：用新 `paths` 重建 `AnyView` 与 `Arc`，刷新 `drag.value` / `drag.view` / `drag.cursor_offset`。
- **原因**：OHOS 在 drag-enter 时先给一个空的 `Entered`，真实路径直到 drop 才送达；不刷新则 drop 监听器拿不到真实路径。
- **重放要点**：对应 `../bugfix/2026-08-21-file-drop-open.md`。

### 3.4 `crates/zlog`：日志改走 hilog

- **改动**：
  - `zlog.rs` 新增 `#[cfg(target_env = "ohos")] pub mod ohos;`；在 `Zlog::log` 过滤之后，OHOS 分支改为 `ohos::submit_to_hilog(record); return;`（不再走文件/stdout sink）。
  - 新增 `crates/zlog/src/ohos.rs`：`#[link(name = "hilog_ndk.z")]` 直接 FFI 到 `OH_LOG_Print`，`log::Level` 一对一映射到 hilog 级别（error=6/warn=5/info=4/debug|trace=3），domain `0x0001`，tag `Zed`。另提供 `direct_hilog_info` 供"全局 logger 尚未注册"的早期启动诊断。
- **重放要点**：该模块**不能用 `log::info!()` 系列**，否则递归回 `Zlog::log`。对应 `../bugfix/2026-08-20-panic-log-to-hilog.md`。

### 3.5 `crates/crashes`：桌面实现与 OHOS 存根拆开

- **改法**（模式 C，**最佳样板**）：
  - 原 `crashes.rs`（约 1029 行）**原样**搬到 `crashes_desktop.rs`（已核对：两者逐字节一致，无任何改动）。
  - 新 `crashes.rs` 只做分发：`#[cfg(not(target_env = "ohos"))] #[path = "crashes_desktop.rs"] mod desktop;` + `#[cfg(target_env = "ohos")] mod ohos { ... }`，末尾 `pub use desktop::*;` / `pub use ohos::*;`。
  - OHOS 存根保持**同一套公开面**：`Client`、`CrashInfo`、`InitCrashHandler`、`CrashPanic`、`UserInfo`、`SENTRY_USER_ID`、`force_backtrace`、`init`、`set_gpu_info`、`set_user_info`、`panic_hook`、`crash_server`。
  - `panic_hook` 在 OHOS 上的行为：`log::error!` 记录 panic 位置与消息（经 zlog 进 hilog）后 `std::process::abort()`。
- **原因**：桌面实现依赖 `minidumper`（→`uds`，其 `ControlLen` 假设在 OHOS libc 不成立）、`crash-handler`、`async-process`、`zstd`，均无法在 OHOS 构建/运行。
- **重放要点**：新版本若给 `crashes` 增加公开 API，**必须同时补进 OHOS 存根**，否则 `zed`/`remote_server` 编译不过。存根的字段/签名要与桌面实现逐一对齐。

## 4 进程执行（cmd-agent 路由）

**核心事实**：OHOS 沙箱禁止 `exec` 任意二进制。所有外部进程（LSP、node、chmod、shell 等）改由设备侧守护进程 `hicodeerd` 执行；仅 `/data/app/bin`（HNP 私有安装目录）里的工具在本进程内 fork 执行。

### 4.1 `crates/util/src/command.rs` 与新增 `command/ohos.rs`

- **`command.rs`**（分发层）：
  - `#[cfg(target_env = "ohos")] mod ohos;` + `pub use ohos::{Child, Command, LocalToolStatus, Stdio, init, init_local_tools, local_tool_programs, local_tool_status};`
  - 原有的 `Child`/`Stdio`/`Command`（`smol::process` 版）全部追加 `not(target_env = "ohos")`。
- **`command/ohos.rs`**（约 820 行，纯新增）职责：
  - `init(socket_path)` 注册远端执行器；`executor()` 取自 `cmd-client` 的 `RemoteCommandExecutor`。

## 9 新增脚本与资源

### 9.1 `script/bundle-ohos`（约 1043 行，主构建脚本）

职责与关键步骤（升级时要复核的接入点）：

- 开头 `unset BASH_ENV` 并 `unset -f rm unlink rmdir`：调用方若把 `rm` 换成包装函数（`BASH_FUNC_*` 导出 + `BASH_ENV` 每层子 shell 重新 source），需要两条一起清，否则脚本在第一次 `rm` 就以 126 静默退出。
- **平台探测**：本机（`~/.harmonybrew/bin/brew` 存在）走 harmonybrew 原生工具链；否则走 openEuler 交叉工具链。
- **`TMPDIR` 钉在 `$PROJECT_ROOT/target/tmp`**：本机 `/tmp` 是只读 erofs，clang 建临时文件失败；且避免 TMPDIR 随调用终端变化导致 cargo 判脏重编。
- **工具链与路径集中配置块**：编译器/链接器（OHOS 原生 clang）、`node`、`hvigorw.js`、`ohpm`、`hap-sign-tool.jar`、`hnpcli`、shim 路径都在此按平台分流，别处不硬编码。
- **hvigor 模块解析**：在 `target/hvigor-node-modules/@ohos/` 下造 `hvigor`/`hvigor-ohos-plugin` 软链，用 `NODE_PATH` 指过去，免得往工程塞 node_modules。
- **固定量**：`OHOS_TARGET="aarch64-unknown-linux-ohos"`、`CRATE="launch-zed"`、`OHOS_LIB_NAME="libhicodeer.so"`（须与 NAPI 模块注册名、`EntryAbility.moduleName` 三方一致）。
- **QEMU 后端开关** `ENABLE_QEMU_AGENT`（默认 `false`）：关闭时 launch-zed 不带 `qemu-agent` feature，guest 侧 hicodeerd、golden 母盘、管理密钥、内核 Image、引擎库都不参与。开启只允许改脚本这一行。
- **资源嵌入**：设备侧调试构建必须开 `util` 的 `debug-embed`，否则 `util::fs_embed!` 会走到"运行时读 checkout"分支并 panic→abort。
- **编译期 shim（LD_PRELOAD）**：本机是 `musllib-shim`（TLS key），openEuler 是 `ohos-meta-shim`（virtiofs EPERM）；只作用于编译进程，调 hvigor/hnpcli/java 前用 `$NO_SHIM`（`env -u LD_PRELOAD`）卸掉。
- **`--check-tls`**：自检 TLS 垫片。
- **hicodeerd 编译 + 固定管理密钥 + HNP 装配**：交叉编译 `hicodeerd`、生成管理密钥、装 `hicodeerd.hnp`。
- **ArkTS 源码同步**：从 cargo git checkout 同步 ArkTS 源（`arkts_revision_from_lock` / `arkts_checkout_dir` / `sync_arkts_sources`）。
- **ohpm install + hvigor assembleHap**：含软链缺失/关键 so 缺失检测与 stale cmake/ninja 清理。

### 9.2 `script/ohos-tls-shim.c`（约 278 行）

- **目的**：绕过 OHOS libc 的 `PTHREAD_KEYS_MAX`（128）上限。`aarch64-unknown-linux-ohos` 的 target spec 设 `tls-model: emulated`（`target_thread_local` 为 false），std 的 `thread_local!` 建在 pthread key 上，一个 TLS 变量一个 key；rustc/cargo/build script/proc-macro dylib 同一进程累积 key 会耗尽并 abort（"out of TLS keys"）。`-Z tls-model=...` 无效（只影响原生 TLS codegen，不改 std 选的实现）。
- **做法**：interpose 四个 pthread TLS 入口，`keys >= VIRTUAL_KEY_BASE` 归 shim；虚拟 key 的值放 per-thread 堆数组，用**单个**真实 pthread key 锚定（全进程最多消耗一个真实 key）；线程退出析构用 musl 语义模拟（先清槽再调析构，最多 `DESTRUCTOR_ITERATIONS` 次）。
- **构建**：`clang -shared -fPIC -O2 -o ohos-tls-shim.so ohos-tls-shim.c -ldl`；`OHOS_TLS_SHIM_DEBUG=1` 打 key 统计。
- **重放要点**：这是**编译期**垫片，只作用于构建进程，不改变产物。升级工具链后要重跑 `--check-tls`。

### 9.3 `script/read-sign-pwd.js`（约 116 行）

- **目的**：从 HAP 工程的 `build-profile.json5` 里解出 DevEco 保存的 keystore 密码（方案公开，hvigor 的 `decipher-util.js` 就是明文实现；per-keystore 随机材料在同目录 `material/`）。用法 `node read-sign-pwd.js <hap-project-dir>`。
- **重放要点**：换 keystore 不需要把密码同步进仓库。上游无关，长期保留。

### 9.4 `install-local.sh`（约 309 行）

- **目的**：本机即设备时的安装/启动脚本。链路：`hdc` 客户端经 TCP 回环连本机 `hdcd` 调试端口。
- **通道优先级**：a) `OHOS_HDC_SERVER_PORT`（默认 18710）→ b) 默认通道 → c) 才尝试新 server。不预先 kill 旧 server；用 `tconn ... -remove` 清重复 target。
- **参数**：`--port <设备调试端口>`、`--server-port N`、`--hap <path>`、`--reinstall`（先卸载再装，**仅用于让 hicodeerd 换新版**）、`--no-start`、`--no-stop`、`--help`。
- **重放要点**：`--reinstall` 会卸应用、清沙箱（用户规则明令禁止未授权使用）。常规装包用不带参数的覆盖安装。相关 skill：`ohos-hdc-connect`。

## 12 2026-10-02 改动：终端桥接回退、本地子进程等待与默认设置/日志演进

本批改动相对上一版是**演进与收敛**，多数是把 OHOS 专属分支**回退到上游形态**：终端不再自建桥接（`ohos_shell.rs`），改由上游既有的 `terminal.shell` 设置项承接；同时把本地子进程的退出观测从 `pidfd` 轮询换成阻塞等待线程（appfreeze 根修），默认设置与日志默认等级改由配置/构建决定。

### 12.1 删除 `crates/terminal/src/ohos_shell.rs`（整文件删除，489 行）

- **改法**：整文件删除；`crates/terminal/src/terminal.rs` 顶部的 `#[cfg(target_env = "ohos")] mod ohos_shell;` 一并删除。
- **原因**：终端 shell 改由上游既有的 `terminal.shell` 设置项承接（见 12.7），OHOS 不再需要自造的 guest pty 桥接（本地 pty 对 + 两条桥接线程 + 停在 FIFO 上的 `/bin/sh`）。
- **重放要点**：升级时不要再重建此模块。

### 12.2 `crates/terminal/src/terminal.rs`：回退到上游形态

- **改法**：
  - `open_pty` 恢复为无条件从 `crate::alacritty` 引入（删掉"OHOS 用 `ohos_shell::open_pty`"的 cfg 分叉）。
  - `TerminalBuilder` 环境准备处删除 `#[cfg(target_env = "ohos")] env.insert("SHELL", "/bin/sh")`。
  - shell 选择处删除 OHOS 的 `Some(ShellParams::new("/bin/sh", None, None))` 分支。
  - `open_pty` 调用点删除 `guest_shell` 探测与分叉，恢复单一的 `open_pty(&pty_options, TerminalBounds::default(), window_id)`。
  - primary selection 的 4 处写入，cfg 由 `all(any(linux, freebsd), not(ohos))` 恢复为上游的 `any(linux, freebsd)`——不再对 OHOS 排除。`write_to_primary` 在 gpui_ohos 后端是空实现（`crates/gpui_ohos/src/ohos/platform.rs` 的 `fn write_to_primary(&self, _item: ClipboardItem) {}`），调用无副作用，故不需要 `not(target_env = "ohos")`。
  - `spawn_task_subprocess` 里 `Stdio` 的 import 由"非 OHOS `std::process::Stdio` / OHOS `util::process::Stdio`"的 cfg 二选一，收敛为无条件的 `use util::process::Stdio;`（`util::process::Stdio` 在非 OHOS 本就是 `std::process::Stdio` 的重导出，两平台等价），并删掉原地的 `[OHOS PORT BEGIN/END]` 标记。
- **原因**：终端 shell 不再由 `terminal.rs` 硬编码 pin `/bin/sh`，而是走 `terminal.shell` 设置项（12.7）；其余 OHOS 分支随之回退。
- **重放要点**：新版本对 `terminal.rs` 只需按需保留"`Stdio` 收敛为无条件 `util::process::Stdio`"这一处（可选，非必需）；SHELL pin / `ShellParams::new("/bin/sh")` / primary selection 排除**都不再需要**。

### 12.3 `crates/terminal_view/src/terminal_panel.rs`：删除"打开即最大化"

- **改法**：删除 `Panel::set_active` 里整段 `#[cfg(target_env = "ohos")] if active && !old_active { cx.emit(PanelEvent::ZoomIn); }`，回到上游形态。
- **原因**：该 OHOS 专属行为本次一并回退（随终端承载方式改变，不再需要打开面板即最大化）。删除理由未在 diff 中另附，此处按删除事实记录。
- **重放要点**：升级时不再添加这段。

### 12.4 `crates/util/src/command.rs`：摘除终端专属远端 shell 出口（修正第 4.1 节）

- **改法**：OHOS 的 re-export 列表由 `{Child, Command, LocalToolStatus, RemoteShell, ResizeHandle, Stdio, init, init_local_tools, local_tool_programs, local_tool_status, open_remote_shell}` 收敛为 `{Child, Command, LocalToolStatus, Stdio, init, init_local_tools, local_tool_programs, local_tool_status}`——去掉 `RemoteShell`、`ResizeHandle`、`open_remote_shell`。
- **原因**：这三个出口专为终端桥接而设（`open_remote_shell` 用于在守护进程/guest 上开交互 shell），终端回退后不再需要。

### 12.5 `crates/util/src/command/ohos.rs`：摘除远端 shell 出口 + 本地子进程退出改阻塞等待（appfreeze 根修，修正第 4.1 节）

- **摘除远端 shell 出口**：删除文末的 `pub use cmd_client::RemotePty as RemoteShell;`、`pub use cmd_client::ResizeHandle;` 与 `pub async fn open_remote_shell(cols, rows, cwd, program, args) -> io::Result<RemoteShell>`。
- **本地子进程改为专用阻塞等待线程**（本批核心）：
  - `spawn_local` 的进程类型由 `smol::process::Command` 改为 `std::process::Command`（加 `#[allow(clippy::disallowed_methods)]`；理由是 `smol::process` 的 pidfd 后端在本内核上会空转，且 spawn 后管道立即设为非阻塞，spawn 本身是快速 fork/exec）。
  - 新增 `LocalChild`：不再用 `async-process` 的 `status()` future，而是启动一条名为 `ohos-local-wait-{pid}` 的线程在 `waitpid` 上阻塞，把退出结果发布到 `Arc<Mutex<LocalExitState>>`（`LocalExit` 为 `Pending`/`Exited`/`Failed`）并唤醒异步等待者；`publish_exit` 负责发布后统一 wake，`poll_exit` 负责注册 waker。
  - 新增 `wrap_child_stdin` / `wrap_child_stdout` / `wrap_child_stderr`（用 `smol::Async::new` 把管道包成异步流，非 piped 描述符映射为 `None`）。
  - 新增 `reap_local_child`：stdio 包装失败时对子进程 kill + `wait` 回收后再返回原始错误，避免"孤儿 + 僵尸"（此前 `?` 会在 `LocalChild` 接管前直接丢弃子进程）。
  - `LocalChild::kill` 改走 pidfd：`open_pidfd` 用裸 `libc::syscall(SYS_pidfd_open, ...)` 打开（该 target 的 libc 无封装）、`send_signal_through_pidfd` 用 `SYS_pidfd_send_signal` 发送；内核不支持 `pidfd_send_signal`（`ENOSYS`）时回退到裸 `libc::kill(pid, signal)` 并打 `log::warn!`。用 pidfd 是为了防止 waiter 线程回收子进程后 pid 被复用、把 SIGKILL 发到别的进程。
  - `apply_local_tool_env` / `local_stdio` 的参数类型由 `smol::process` 改为 `std::process`。
  - `ChildKind::Local` 字段类型由 `smol::process::Child` 改为 `LocalChild`；`Child::status()` 的本地分支适配为 `Box::pin(child.status())`。
- **原因**：`pidfd_open` 在 HarmonyOS 上返回有效描述符，却在该描述符上过早报告可读——`async-process` 仅凭 `pidfd_open` 成功就选 pidfd 后端，于是 `WaitableChild::poll_wait` 永不阻塞，`try_wait → poll_readable` 在驱动该 future 的线程（观测到的冻结里是前台线程）满 CPU 空转。改用一条阻塞 `waitpid` 线程接管退出观测，异步侧只等唤醒即可。
- **重放要点**：这是第 4.1 节"本地子进程"实现的替换；新版本重放时应直接用 `LocalChild` 方案，**不要退回 `smol::process`**。

### 12.6 `crates/zlog/src/filter.rs`：默认日志等级改由 `HICODEER_LOG_LEVEL` / build profile 决定

- **改法**：`LEVEL_ENABLED_MAX_DEFAULT` 拆成两个 cfg 常量，并新增编译期取值：
  - 新增 `const ENV_LEVEL: Option<log::LevelFilter> = match option_env!("HICODEER_LOG_LEVEL") { ... }` 与 `const fn level_filter_from_str_const`（ASCII 大小写不敏感，识别 `trace`/`debug`/`info`/`warn`/`error`/`off`，无法识别则返回 `None`）。
  - OHOS：`ENV_LEVEL` 优先；否则 `cfg!(debug_assertions)` 为真取 `Info`，否则取 `Warn`。
  - 非 OHOS：`ENV_LEVEL` 优先；否则维持上游的 `Info`。
- **原因**：让构建脚本用 `HICODEER_LOG_LEVEL` 一次性重定向所有日志 sink（`const` 因此是硬约束，值要喂给下方的 `const` 默认值）；release 构建在无覆盖时回落到 `Warn`，减少设备侧日志量。
- **重放要点**：`HICODEER_LOG_LEVEL` 由 `script/bundle-ohos` 导出（属构建脚本，见第 9.1 节）；与第 3.4 节的 zlog→hilog 是同一 crate 的过滤层。

### 12.7 `crates/settings/src/settings.rs`：OHOS 叠加合并 `default-ohos.json`

- **改法**：`default_settings()` 拆为两个 cfg 版本：
  - 非 OHOS：维持上游的 `asset_str::<SettingsAssets>("settings/default.json")`。
  - OHOS：新增实现——以 `settings/default.json` 为基础、`settings/default-ohos.json` 为增量，用新增的 `merge_default_overlay(base, overlay)` 叠加后返回。`merge_default_overlay` 用 `serde_json::Value` 解析两份文本（`parse_json_with_comments`），调 `settings_content::merge_from::MergeFrom` 深合并，再序列化回字符串；失败时 `log::error!` 并回退到未叠加的基础值。
- **原因**：OHOS 专属默认值（含本批新增的 `terminal.shell.program = "/data/app/bin/hishell"`）落成 JSON 增量而非代码改动。`MergeFrom` 与设置存储合并用户设置用的是同一套递归合并，故增量只覆盖指定键、其余继承基础默认值。
- **重放要点**：`settings/default-ohos.json` 保持"只放增量"的写法；`terminal.shell` 是终端重定向到 hicodeerd 的唯一开关（与 12.1~12.3 配套）。
