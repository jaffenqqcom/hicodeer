# 第 7 章 新增文案归类（160 条怎么处理）

第 5 章算出的「仅 1.23 有」共 **160 条**，本章把这 160 条分层，决定各自怎么处理。

## 7.1 分层结果（合计 160）

- **必须补译 · 我们自己的文案：28 条**
  - 全部在 `crates/settings_content/src/qemu.rs`（实测：该文件在 `needs_review` 中出现 **28** 次，与 28 条一致）。
  - 内容：QEMU guest 的 CPU / RAM / 磁盘档位设置——`Cpu1..Cpu10`、`Mem4/6/8/10/12`、`Disk64/96/128/256/512`，外加 8 条说明。
  - 判定依据：该文件由**我们的 commit 引入**，文件头明确写着 `HarmonyOS builds where an embedded QEMU guest can host the LSP servers and the terminal`（实测文件头注释）。
- **需要补译 · 上游新功能可见文案：22 条**
  - 如 `Unstage Folder`、`Up to Date`、`Failed to load OpenCode {} models: {error}`、Threads Sidebar 系列设置项。
- **可延后 · 上游文档类：62 条**（`rust_doc_comment`）。
- **不需要翻译 · 误抓：48 条**
  - **40 条**是 doc 注释里的 JSON / 配置片段；
  - **6 条**是测试串；
  - **1 条**是 `key_context: "menu"` 这类键上下文 id；
  - **1 条**是分隔符 `Label::new("· {model_name}")`。

28 + 22 + 62 + 48 = 160。

**实测备注（口径说明）**：对 1.23 manifest 的 `needs_review` 条目按 kind 统计，`rust_doc_comment` 的 occurrence 达 **152 处**，为最大宗。上面的「62 条」是**「清单3」的筛选口径**（见第 8 章：从「其余新增键」里的 `rust_doc_comment` 再排除以 `"` 开头的 40 条代码/配置行后所得），不是 `needs_review` 里 doc 类的总数；两者不要混用。

## 7.2 关键结论

- **我们改动过的那 11 个撞车文件贡献 0 条新增文案**——我们改的地方没有引入新文案，所以回注时不会被「我们的改动」和「它的改动」同时打在同一处文本上。

## 7.3 「纯上游」新增的 128 条

- 对话记录：**纯上游 128 条**（剔除误抓后 **81 条有效**）。
- 其中：
  - **改写 72 条**（上游把旧的英文句子改了措辞）；
  - **真新增 9 条**（确实是新出现的句子）；
  - **不确定 0 条**。
  - 72 + 9 = 81，与「81 条有效」自洽。
- 判定方法：用「设置项 / 功能锚点」在 **1.21 键集合**里找语义对应的旧句，能对应的判为「改写」，找不到对应旧句的判为「真新增」。
- **实测备注**：「128」的口径未能在本轮从产物精确复核（160 − 28 = 132，与 128 有 4 条差），标注**未核实**；「81 = 72 + 9」内部自洽。
